## 3. 项目资产的双重版本管理

AI Coding时代需要同时管理两类项目资产：

1. **科研软件资产**：仿真场景、数据接口、算法、控制器、测试和实验配置；
2. **Agent资产**：Agent规则、角色、工作流、Skill、提示模板和Agent评测用例。

两类资产都必须进入同一个Git仓库、共同评审和版本化。任何Agent或Skill变化都有可能影响生成的代码与实验流程，因此也属于实验可复现性的一部分。

### 3.1 建议目录结构

```text
workspace/
├── README.md
├── AGENTS.md                       # 全项目Agent行为与目录约束
├── pyproject.toml                  # Python项目与工具配置
├── configs/                        # 仿真、建模、控制和实验配置
├── src/                            # 扁平源码结构，不增加项目名二级目录
│   ├── simulation/
│   │   ├── examples/               # 固定版本的官方示例适配入口
│   │   └── scenes/                 # 本课题自有SOFA场景
│   ├── modeling/                   # 数据处理和动力学建模
│   ├── control/                    # 基础控制、MPC和SAC
│   └── evaluation/                 # 指标、曲线和可视化
├── tests/
│   ├── smoke/                      # SSH、GPU和SOFA基础设施检查
│   └── integration/                # 科研链路测试
├── scripts/
│   ├── remote/                     # 本地发起SSH任务
│   └── server/                     # 登录远端后直接执行
├── agent/
│   ├── README.md                   # Agent框架边界和使用方法
│   ├── workflows/                  # 可重复的科研工作流
│   ├── skills/                     # 项目级Skill权威源码
│   └── registry.yaml               # 名称、版本、负责人和状态
├── docs/
├── datasets/                       # 轨迹和训练数据，默认不提交大文件

```

`agent/` 是项目级Agent资产的权威来源。某个AI工具的全局Skill安装目录或缓存目录只是部署副本，不能成为唯一来源；后续通过安装/同步脚本从项目目录部署。

## 5. Agent框架与Skill库计划

### 5.1 Agent角色

第一阶段只建立必要角色，避免过度设计：

| 角色 | 职责 | 不负责的事项 |
|---|---|---|
| Research Planner | 拆解里程碑、管理依赖和验收标准 | 擅自改变研究问题 |
| Simulation Engineer | SOFA场景、求解器、控制输入和数据导出 | 宣称物理模型已经标定 |
| Experiment Operator | 同步、启动、监控、回传和元数据 | 删除历史结果 |
| Result Auditor | 检查数据完整性、泄漏、指标和可复现性 | 只凭单次曲线下结论 |

### 5.2 首批Skill

优先建设三个高复用Skill：

1. `remote-experiment-operator`：规范同步、run ID、远端运行、状态和回传；
2. `sofa-scene-validator`：检查插件、组件、输入响应、数值稳定性和输出字段；
3. `experiment-result-auditor`：检查元数据、轨迹切分、NaN、哈希、指标和图表。

建模、控制和报告Skill在科研接口稳定后再增加，避免把尚未验证的方法过早固化。

### 5.3 Skill最小规范

每个Skill目录至少包含 `SKILL.md`，明确：

- 适用场景和触发条件；
- 输入、输出和前置条件；
- 允许使用的工具和路径范围；
- 标准工作步骤；
- 验收标准和失败条件；
- 安全限制；
- 一个成功示例和一个失败示例；
- 版本和变更记录。

如果Skill需要脚本、模板或参考资料，应放在该Skill目录下，不在提示中复制多个失去同步的版本。

### 5.4 Agent/Skill质量门禁

Agent框架不能只靠“看起来合理”的文字验收。相关用例统一放在`tests/integration/`，至少覆盖：

- 能否把文件放入正确目录；
- 是否拒绝覆盖已有run ID；
- 是否避免上传凭据和本地配置；
- 是否生成完整实验元数据；
- 是否识别仿真日志中的错误、NaN和不稳定状态；
- 同一任务在Skill升级后是否仍得到结构一致的产物。

任何Skill修改必须先通过相关回归用例再合入 `main`。Agent生成的科研结论仍需人工审核；物理参数、实验对照和论文结论不能由Agent自行决定。

## 6. SOFA官方Demo验证计划

不以“下载并打开大量Demo”为目标，而是按能力选择少量固定示例。当前安装包已经包含官方示例，优先使用随SOFA v25.12.00发布的版本；需要复制或修改时记录来源、版本和许可证，不直接修改运行环境中的原文件。

建议验证四类场景：

1. **基础柔性体FEM**：验证网格、材料、固定约束和时间积分；
2. **CableConstraint**：用程序自动施加位移/拉力，验证绳驱响应；
3. **Trunk或多绳连续体**：验证多绳输入与空间弯曲；
4. **Python数据导出**：每步输出输入、中心线状态和末端位姿。

每个Demo必须满足：

- batch和GUI至少一种方式可运行；
- 不依赖人工键盘输入才能产生响应；
- 输入变化能在数值状态中被检测；
- 输出CSV和运行元数据；
- 固定SOFA版本、场景来源和配置；
- 无错误、NaN或无界发散；
- 重复运行得到可解释的一致结果。

## 7. 自有仿真与数据接口

官方Demo验证后，立即建立本课题自己的简化模型。第一版不追求复现实机全部几何，建议使用单段、三绳或四绳结构，先跑通接口。

统一仿真接口：

```python
reset(seed, config) -> observation
step(cable_command) -> observation, diagnostics
save_trajectory(path)
```

第一版轨迹至少记录：

- 时间与步号；
- 各绳位移、目标拉力和实际约束力；
- 末端位置；
- 若干中心线采样点；
- 仿真步长和求解器状态；
- 是否出现NaN、发散或约束失败。

必须先完成以下测试：

- 零输入平衡；
- 相同输入确定性；
- 对称绳索输入的对称性；
- 单绳输入方向合理性；
- 输入上下限和异常恢复；
- 不同时间步长下的基本稳定性。

## 8. 算法框架推进顺序

不直接从SAC或复杂PINN开始。推荐顺序：

1. 线性回归/状态空间模型；
2. 小型MLP动力学模型；
3. 标准Koopman模型；
4. 融合物理先验的Koopman或PINN；
5. 基础开环预测和MPC闭环；
6. 最后接入SAC并与基础控制器比较。

训练集、验证集和测试集按完整轨迹划分，禁止随机混合相邻时间步造成数据泄漏。评价同时报告单步误差、多步滚动误差、末端误差、稳定性和计算时间。

## 11. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 官方示例可显示但无法自动驱动 | 编写自己的Python Controller，不依赖键盘事件 |
| SOFA模型复杂度过高 | 先用简化几何、较粗网格和单段结构 |
| 仿真数据生成过慢 | 关闭渲染、减小网格、并行多个独立轨迹 |
| 模型效果差 | 保留线性/MLP Baseline，优先保证完整链路 |
| Agent修改导致流程漂移 | Agent/Skill与代码同仓库版本化，并执行回归评测 |
| 远端实例重建 | 环境可重建，代码和关键结果保存在共享存储与本地 |
| 临近答辩演示失败 | 提前准备固定配置、日志、曲线和录屏备用 |
