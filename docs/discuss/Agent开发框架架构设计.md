# Agent 开发框架架构设计

> 日期：2026-09-30  
> 状态：架构原则已确定，具体实现待后续设计  
> 范围：面向本项目持续开发、实验评测和自动迭代的 Agent 框架

## 1. 建设目标

本框架的目标不是简单增加若干独立 Agent，而是建立一个能够持续运行的项目迭代闭环：

```text
观察项目与实验状态
→ 评测结果并诊断问题
→ 规划和实施修改
→ 重新运行验证
→ 发布或回滚
→ 沉淀经过验证的经验
```

框架应逐步支持：

- 自动评估项目里程碑和实验进度；
- 根据日志、指标、曲线和运行状态诊断问题；
- 自动完成代码实现、调试和实验优化；
- 对修改结果重新评测，形成可重复的修复循环；
- 保留长期项目知识，避免反复犯同一类错误；
- 在明确的权限、资源和人工审批边界内运行。

## 2. 总体架构

框架由五个相互协作的平面组成：

1. 评测与反馈平面；
2. 编排与实现平面；
3. 工具与运行时平面；
4. 上下文与知识平面；
5. 治理与控制平面。

它们不是简单的上下层调用关系，而是一个受治理约束、由知识支撑的反馈控制系统：

```text
                         治理与控制平面
              目标、权限、预算、审批、停止、回滚
                                │
                                ▼
评测与反馈 ──结构化诊断──→ 编排与实现 ──受控动作──→ 项目与实验环境
     ▲                              │                       │
     │                              └────重新验证───────────┘
     │                                                      │
     └──────── 日志、指标、轨迹、图表和运行状态 ────────────┘

               工具与运行时平面贯穿观察和执行
               上下文与知识平面支撑所有决策
```

## 3. 评测与反馈平面

### 3.1 设计目标

把项目状态、实验结果和运行异常转换成有证据、可执行、可复验的反馈。

### 3.2 核心职责

- 根据验收标准判断项目里程碑是否完成；
- 检查实验完整性、可复现性和指标变化；
- 分析日志、监控数据、轨迹、曲线和可视化结果；
- 发现错误、性能退化、异常趋势和潜在科研风险；
- 形成结构化的问题诊断、证据、置信度和验收条件；
- 在修改完成后使用相同标准重新评测。

### 3.3 设计原则

- 先使用测试、统计和领域规则，再使用 Agent 解释复杂现象；
- 项目进度必须由产物和验收结果证明，不能只依赖文字声明；
- 诊断结论必须关联日志、指标、commit 或实验 run；
- 评测标准独立版本化，实现 Agent 默认不得修改评测标准；
- 评测层只提供诊断和建议，不直接修改代码。

## 4. 编排与实现平面

### 4.1 设计目标

根据评测层提供的证据和反馈，规划并执行代码实现、问题修复、性能优化和实验迭代。

### 4.2 核心职责

- 接收并理解结构化诊断；
- 判断问题类型、优先级、依赖和风险；
- 在证据不足时请求补充检查或实验；
- 制定可验证的实施计划；
- 调度代码修改、调试、测试和实验任务；
- 将修改交回评测层验证；
- 根据验证结果继续迭代、停止或回滚。

### 4.3 循环类型

- **确定性修复循环**：测试失败、代码错误、接口或格式问题；
- **性能优化循环**：运行速度、资源消耗、预测误差和控制精度；
- **科研探索循环**：模型结构、实验设计和研究假设。

三类循环采用不同的自动化程度。确定性修复可以高度自动化；性能优化需要固定基线和资源预算；科研探索必须保留人工判断。

## 5. 工具与运行时平面

### 5.1 设计目标

为所有 Agent 提供稳定、确定、可观测和受权限控制的操作能力。

### 5.2 能力范围

- 代码搜索、编辑、测试和静态检查；
- Git、差异比较、隔离工作区和版本查询；
- 本地与远程任务启动、监控、停止和结果回传；
- 日志、指标、GPU、CPU、内存和进程监控；
- 数据、配置、轨迹和模型产物校验；
- 曲线、图表、视频和报告生成；
- 沙箱、超时、资源锁、预算和审批接口；
- trace、事件和 artifact 存储。

### 5.3 设计原则

- 工具本身尽量采用确定性程序，不必全部实现成 Agent；
- 输入输出使用明确 schema；
- 读取和写入权限分离；
- 副作用、目标路径和资源消耗必须显式；
- 支持幂等、dry-run、错误码和可重试行为；
- 不允许把不可信自由文本直接转换成高权限操作。

## 6. 上下文与知识平面

### 6.1 设计目标

为各层提供经过筛选、可追溯、与当前任务相关的项目知识，使系统能够跨任务和跨实验持续改进。

上下文平面不是简单保存全部对话，也不是由一个 Agent 自由维护所有记忆，而是共享的知识基础设施。

### 6.2 知识分类

| 类型 | 内容 | 生命周期 |
|---|---|---|
| 工作记忆 | 当前目标、最新反馈、未完成计划 | 单次任务 |
| 情景记忆 | 某次实验、失败、修复和验证过程 | 长期，按 run 查询 |
| 语义知识 | 已确认的项目事实、接口、单位和领域知识 | 长期，版本化 |
| 决策记录 | 方案选择、取舍理由和被拒绝方案 | 长期，人工审核 |
| 程序知识 | SOP、工作流、Skill 和检查清单 | 长期，版本化 |
| 原始历史 | 完整日志、trace、指标和实验产物 | 不可变、按需检索 |

### 6.3 写入原则

```text
原始观察
→ 候选记忆
→ 来源验证、去重和冲突检查
→ 标记版本、置信度和适用范围
→ 规则或人工审批
→ 写入长期知识
```

- 原始日志不直接等于长期知识；
- Agent 总结不自动成为项目事实；
- 关键知识必须记录来源、时间、commit/run 和验证状态；
- 过期或冲突知识应保留历史关系，而不是静默覆盖；
- Git 文档和实验原始产物是权威证据，检索索引不是唯一可信来源。

### 6.4 读取原则

每个任务只加载必要上下文。上下文构建结果至少包含：

- 当前目标；
- 约束和权限；
- 当前项目状态；
- 相关历史实验和失败；
- 已确认决策；
- baseline 和验收条件；
- 原始证据链接。

## 7. 治理与控制平面

### 7.1 设计目标

控制整个闭环可以做什么、可以运行多久、何时需要人工确认，以及失败后如何安全停止或回滚。

它负责约束自动化，而不是替代编排层完成任务。

### 7.2 核心职责

- 管理系统目标、优先级和允许的任务范围；
- 管理 Agent、工具、路径和远程资源权限；
- 设置时间、token、GPU、存储和最大迭代预算；
- 设置人工审批点；
- 防止并发任务互相覆盖；
- 定义成功、停止、升级和回滚条件；
- 保护评测标准、历史实验和科研结论；
- 保存完整审计记录。

### 7.3 风险边界

- 只读分析和本地检查可以自动执行；
- 代码修改只能先进入隔离环境；
- 远程实验必须受到运行时间和资源预算限制；
- 修改研究方案、合并代码和发布结论需要人工确认；
- 删除数据、覆盖历史实验和绕过评测标准禁止自动执行。

### 7.4 与编排层的区别

- 编排层决定“如何完成任务”；
- 治理层决定“是否允许做、允许做到什么程度、什么时候必须停止”。

治理能力优先由规则、状态机、权限系统和人工审批实现，不依赖 Agent 自律。

## 8. 层间接口

各层之间不直接传递大段自由文本，应使用结构化事件和 artifact 引用。典型事件包括：

```text
RunCompleted
EvaluationFailed
DiagnosisProduced
ChangeProposed
ImplementationCompleted
ValidationPassed
ValidationFailed
ApprovalRequired
ChangePromoted
ChangeRolledBack
KnowledgeCandidateProduced
```

评测层交给编排层的反馈至少应包含：

- 目标对象；
- 问题现象；
- 证据引用；
- 预期与实际差异；
- 候选原因及置信度；
- 建议检查方向；
- 验收标准；
- 风险等级。

## 9. 闭环状态模型

一次完整迭代采用以下状态：

```text
OBSERVED
→ EVALUATED
→ DIAGNOSED
→ PLANNED
→ IMPLEMENTED
→ VERIFIED
→ PROMOTED / REJECTED / ROLLED_BACK
→ LEARNED
```

每次状态变化都必须产生可追踪的结构化记录。只有通过验证的结果才能进入正式代码或长期知识。

## 10. 核心设计原则

1. 评测者与实现者分离；
2. 诊断、决策、执行和验证分离；
3. 工具负责确定执行，Agent 负责判断和编排；
4. 原始数据、反馈和长期知识分离；
5. 候选修改与正式状态分离；
6. 自动修复与科研判断分离；
7. 所有结论和动作可追溯；
8. 所有循环有预算、停止条件和回滚路径；
9. 只有经过验证的经验才能进入长期知识；
10. 自动化程度随证据可靠性和风险逐步提升。

## 11. 框架成熟度路线

- **阶段 0：观察**——自动采集日志、指标、产物和项目状态；
- **阶段 1：评测**——自动评测和诊断，由人决定如何修改；
- **阶段 2：辅助闭环**——Agent 提出并实施候选修改，由人审核；
- **阶段 3：受控自动修复**——低风险问题可在沙箱内自动迭代；
- **阶段 4：有限自治优化**——在预算、评测和回滚约束内自动优化；
- **阶段 5：科研协作**——Agent 支持实验探索，但研究决策和结论保持人工负责。

项目应从可观察、可评测和可回滚开始，逐步提升自治程度，而不是一开始追求全自动运行。

## 12. 架构成功标准

一个有效的 Agent 开发框架应做到：

> 每次判断有证据，每次动作可追踪，每次修改可验证，每次失败能沉淀，每次自动化有边界。
