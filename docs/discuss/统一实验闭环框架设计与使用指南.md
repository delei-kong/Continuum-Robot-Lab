# 统一实验闭环框架设计与使用指南

> 日期：2026-10-05  
> 状态：V1 长期架构与操作基线  
> 适用范围：实验入口、Pipeline 编排、算法接入、场景执行、评估可视化、批量实验和远程运行

## 1. 目标与边界

项目采用统一实验闭环框架，目的是让场景、算法、Pipeline、评估和可视化通过稳定合同协作，停止按
具体实验组合复制 Shell 脚本。

框架允许按实质不同的生命周期保留少量领域入口，不追求形式上的唯一入口。只有生命周期、运行环境或
输入输出合同存在明显差异时，才应新增领域入口；仅改变输入、算法、seed、显示模式或输出名称时，不得
新增脚本。

统一框架 V1 完成时，`scripts/` 下 `.sh + .py` 的脚本基线为 24。脚本数量是治理指标而不是机械目标；
新增脚本必须说明现有入口、注册表或子命令无法承载的原因。

## 2. 总体架构

统一实验执行链路为：

```text
领域执行入口
  → 受控的 Pipeline / 算法 / 输入注册表
  → 配置解析、约束验证与 RunManifest
  → 统一执行内核
      validate → preflight → prepare → run → verify → finalize
  → 本地 SSH / 远端 batch / 远端 GUI 薄适配器
  → 标准运行产物
  → 评估、可视化、批量汇总与结果回传
```

机器人控制闭环为：

```text
输入或参考轨迹
  → 控制器 / 算法
  → 仿真或真实后端
  → 状态观测与反馈
  → 控制器（循环）
  → 记录器、评估器和只读可视化
```

各层职责如下：

- 领域入口表达操作者希望运行的实验类型；
- 注册表只允许经过验证的 Pipeline、算法和输入组合；
- 配置文件保存物理、求解、时间、评估和显示细节；
- `RunManifest` 是入口与运行内核之间唯一的已解析请求；
- 执行内核统一处理预检、运行目录、日志、超时、退出码、验证和完成状态；
- 场景只承担后端适配，不重新实现实验级编排；
- 评估、可视化和回传只消费标准运行产物或只读运行时观测。

Pipeline 负责组合输入、算法、后端、记录器和评估器。本地 SSH 与远端工作区脚本只能是薄适配器；
实验选择、步数推导、验证和结果语义不得复制到 Shell 中。

## 3. 参数、配置与不变量

命令行只表达高层实验意图：

- 领域或 Pipeline；
- 已注册算法；
- 已注册输入、轨迹、数据集或模型；
- 输出 run ID；
- batch/GUI 和 local/server 执行方式。

以下细节由受版本管理的配置或预设管理：

- 仿真步长、控制频率和持续时间；
- 轨迹控制点、工作空间和随机生成边界；
- 物理参数、求解器和插件；
- 预热、deadline、评估阈值和输出字段；
- 颜色、线宽和标记大小等显示参数。

不得增加通用 `--set key=value`、任意 Python 模块名、任意场景路径或任意远端路径参数。新增可选项前，
必须先形成经过验证的代码注册项和支持组合。

以下约束属于代码不变量，不得由普通命令行参数关闭：

- `duration / dt` 必须为整数；
- 控制频率必须与仿真步长匹配；
- 初始参考必须与场景初始状态一致；
- 控制器命令类型必须与后端兼容；
- 输出只能写入当前 run 目录；
- run ID 不得覆盖已有运行；
- batch 与 GUI 必须保持相同的控制、记录和评估语义。

每次运行必须生成请求配置、有效配置和元数据快照；任何配置或运行产物都不得包含密码、私钥或访问令牌。

## 4. 当前实现映射

当前 tracking 与正向数据采集主链路由以下模块组成：

| 层次 | 当前实现 |
|---|---|
| tracking 用户入口与受控注册 | `scripts/experiment/run_tracking.py`、`src/experiment/tracking_cli.py` |
| 正向数据用户入口与受控注册 | `scripts/experiment/run_forward_data.py`、`src/experiment/forward_data_cli.py` |
| Koopman 数据集组装与审计 | `scripts/experiment/audit_koopman_dataset.py`、`src/modeling/koopman_dataset_cli.py` |
| Koopman 模型训练与预测评价 | `scripts/experiment/train_koopman.py`、`src/modeling/koopman_model_cli.py`、`src/modeling/koopman_model.py` |
| Koopman-MPC 直驱控制 | `scripts/experiment/run_koopman_mpc.py`、`src/experiment/koopman_mpc_cli.py`、`src/control/koopman_mpc_controller.py` |
| 运行合同 | `src/experiment/contracts.py` |
| 统一执行内核 | `src/experiment/runtime.py` |
| 本地到远端适配 | `scripts/remote/run_experiment.sh` |
| 远端 batch/GUI 适配 | `scripts/server/run_experiment.sh` |
| 控制与 Pipeline 合同 | `src/control/tracking_contracts.py`、`src/simulation/tracking_pipeline.py` |
| SOFA 场景适配 | `src/simulation/scenes/trunk_trajectory_tracking.py`、`trunk_inverse_tracking.py`、`trunk_forward_data.py`、`trunk_koopman_mpc.py` |
| 记录与评估 | `src/evaluation/` |
| 统一结果回传 | `scripts/remote/fetch_run.sh` |

具体文件会随重构演进，但分层职责和依赖方向应保持稳定。

## 5. 标准使用方法

### 5.1 查看受支持组合

```bash
python scripts/experiment/run_tracking.py --list
python scripts/experiment/run_tracking.py --list-batches
python scripts/experiment/run_forward_data.py --list
python scripts/experiment/run_forward_data.py --list-batches
python scripts/experiment/audit_koopman_dataset.py --list
python scripts/experiment/train_koopman.py --list
python scripts/experiment/run_koopman_mpc.py --list
```

### 5.2 从本地发起单个远端 batch 实验

```bash
python scripts/experiment/run_tracking.py \
  --input ellipse \
  --algorithm reference_goal \
  --output <run_id>
```

本地入口会把已解析的 `RunManifest` 交给远端薄适配器。操作者不能通过命令行构造场景、配置或远端路径。

正向数据采集使用独立的领域入口，因为其输入合同为激励预设、其核心产物为状态—动作—下一状态序列；
执行内核、远端适配器与结果回传仍与 tracking 共用：

```bash
python scripts/experiment/run_forward_data.py \
  --input multisine_pilot \
  --output <run_id>
```

### 5.3 运行受控批量矩阵

```bash
python scripts/experiment/run_tracking.py \
  --batch baseline_trajectories \
  --algorithm reference_goal \
  --output <batch_id>
```

当前 `baseline_trajectories` 固定包含 line 和 ellipse。每个 case 使用
`<batch_id>__<input>` 独立 run ID 和远端运行目录。某个 case 失败会写入汇总，但不会阻止后续 case；
批次产物写入：

```text
outputs/tracking_batches/<batch_id>/
├── batch_manifest.json
├── summary.json
└── summary.csv
```

批量矩阵必须在代码中显式登记，不得把该入口扩展成任意参数扫描器。

Koopman 正向数据使用 train、validation、test 三个受控 batch；每个 batch 仍通过同一正向数据入口，
并在 `outputs/forward_data_batches/<batch_id>/` 写入可审查的 case manifest 与汇总。完成回传后，
数据集审计入口只接受注册数据集和这些 batch 输出 ID，拒绝任意 CSV 路径。审计通过后必须以同一入口物化
到 `datasets/<dataset_id>/<release_id>/` 的规范 release；原始运行结果继续保留在 `outputs/`，模型只读取
release 中带 SHA-256 的按 split transition NPZ。

Koopman 训练同样是独立领域入口：它只接收注册数据集、已通过审计的数据集输出 ID 与新的模型输出 ID。
模型配置、训练集归一化、候选模型和多步预测口径均由版本化配置控制，不能以命令行替换：

```bash
python scripts/experiment/train_koopman.py \
  --model koopman_v2_rff_candidates \
  --dataset koopman_v1 \
  --dataset-release <release_id> \
  --output <validation_output_id> \
  --stage validation
```

模型输出位于 `outputs/koopman_models/<model_output_id>/`。验证集用于选择候选 Koopman 模型，测试集
只报告一次最终的一步和多步预测；两者都按原始 episode 边界滚动，不会拼接轨迹。测试阶段必须显式引用
验证选择输出，训练器会核对其模型配置和数据集哈希：

```bash
python scripts/experiment/train_koopman.py \
  --model koopman_v2_rff_candidates \
  --dataset koopman_v1 \
  --dataset-release <release_id> \
  --output <final_output_id> \
  --stage final \
  --selection <validation_output_id>
```

K-MPC 是独立的直驱控制入口：它只接受注册轨迹输入（`line`、`ellipse`、`circle`、`triangle`、`square`），
配置固定引用一个已完成 final 评价的模型输出；运行时读取模型包的 validation 选择结果，直接优化 8 路
绳索位移，并每步以完整 SOFA 状态重新规划：

```bash
python scripts/experiment/run_koopman_mpc.py \
  --input line \
  --output <run_id>
```

### 5.4 在远端 XFCE 运行 GUI

```bash
cd /root/gpufree-share/Continuum-Robot-Lab/workspace
python scripts/experiment/run_tracking.py \
  --input ellipse \
  --algorithm reference_goal \
  --output <run_id> \
  --mode gui \
  --target server
```

GUI 与 batch 使用相同配置、控制循环、记录器和 verifier；GUI 只增加显示和人工观察，不改变实验语义。

K-MPC GUI 同样不改变控制语义：

```bash
python scripts/experiment/run_koopman_mpc.py \
  --input line \
  --output <run_id> \
  --mode gui --target server
```

### 5.5 验证并回传结果

```bash
scripts/remote/fetch_run.sh <profile> <run_id>
```

tracking 当前使用 `trajectory_tracking` 或 `trunk_inverse_tracking` profile；正向数据采集使用
`trunk_forward_data` profile；K-MPC 使用 `koopman_mpc_tracking` profile。不得重新增加按轨迹、算法或数据预设命名的 `fetch_*.sh`。profile 负责定义
必需产物和回传后的验证规则。

### 5.6 运维入口

```bash
# 自动同步
scripts/remote/auto_sync.sh start
scripts/remote/auto_sync.sh status
scripts/remote/auto_sync.sh stop

# PyTorch/GPU 冒烟生命周期
scripts/remote/smoke.sh setup
scripts/remote/smoke.sh sync
scripts/remote/smoke.sh run <run_id>
scripts/remote/smoke.sh status <run_id>
scripts/remote/smoke.sh verify <run_id>
```

自动同步必须保留远端漂移保护。完整本地与远程操作顺序以
`docs/本地开发与远程实验工作流SOP.md` 为准。

## 6. 运行合同与标准产物

run ID 只允许字母、数字、点、下划线和短横线；运行目录一旦存在必须拒绝覆盖。

正式运行至少包含：

```text
<run_id>/
├── requested_config.json
├── effective_config.json
├── metadata.json
├── stdout.log
├── exit_code
├── trajectory.csv、episode.csv 或其他业务产物
├── performance.json 或其他评估产物（按 Pipeline 合同要求）
└── COMPLETE 或 FAILED
```

成功运行至少满足：

- `exit_code=0`；
- 存在 `COMPLETE` 且不存在 `FAILED`；
- 必需产物存在且非空；
- 记录行数、数值有限性和指标结构符合配置；
- 日志不包含已声明的致命错误。

评估与可视化只能读取标准记录或运行时观测，不得通过绘图文件或 CSV 反向驱动控制循环。生成结果写入
`runs/` 或 `outputs/`，不得混入源码目录。

## 7. 扩展方法

### 7.1 新增输入或轨迹

1. 实现输入或轨迹组件；
2. 增加受版本管理的配置；
3. 在受控注册表中登记支持组合；
4. 补充配置推导和边界测试；
5. 运行 batch 自动验收和 GUI 人工验收。

不得为新轨迹增加 Bash 包装器。

### 7.2 新增控制器或算法

1. 实现统一参考、观测、命令和控制器合同；
2. 登记算法及其明确支持的 Pipeline 组合；
3. 复用现有场景适配器、执行内核、记录器和评估口径；
4. 在相同输入和指标下与既有基线比较；
5. 补充自动测试和人工可视化验收。

不得为新控制器复制 SOFA 场景或运行脚本。

### 7.3 新增批量实验

- 只登记有限、可审查的高层实验矩阵；
- 每个 case 使用独立 run ID 和运行目录；
- 单 case 失败不覆盖已完成结果，也不阻止后续 case；
- 持久化批次 manifest、JSON/CSV 汇总和失败信息。

### 7.4 新增后端或领域入口

新后端应实现统一命令与观测映射，并通过薄执行适配器接入，不得把算法选择和配置解析写入场景。

只有生命周期、运行环境或输入输出合同存在实质差异时，才允许新增领域入口。新增前应优先确认现有入口、
manifest、执行内核、verifier、fetch profile 或子命令是否能够承载。

## 8. 测试与验收

涉及统一入口、manifest、生命周期、产物合同或远程适配器的改动，至少覆盖：

- 注册解析与非法组合拒绝；
- 配置不变量和路径边界；
- batch/GUI 的共享语义；
- 失败状态、case 隔离和批量汇总；
- 标准产物及回传验证。

机器人运动、控制效果和场景显示必须继续执行人工 GUI 验收。自动测试、日志和数值指标不能代替人工确认；
具体要求遵循根目录 `AGENTS.md` 的“阶段验收”章节。
