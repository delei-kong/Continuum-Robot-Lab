# 统一实验执行框架需求分析

> 日期：2026-10-03  
> 状态：需求基线 V1；tracking 阶段 A、阶段 B 已实施并验收
> 适用范围：实验入口、Pipeline 编排、远程执行、结果验证与脚本治理

## 1. 背景

项目代码已经初步分为场景、算法库、Pipeline、评估和可视化等层次。实验执行时，
Pipeline 负责组合轨迹、控制器、仿真后端、记录器和评估器，并在 SOFA 场景或其他
后端中运行。

当前的主要问题不是缺少单次控制闭环，而是实验级编排仍分散在多个 Bash 脚本中。
过去按具体实验、轨迹和显示方式持续增加脚本，已导致入口数量增长、运行合同重复、
配置事实来源不唯一，也增加了后续新控制器和批量实验的接入成本。

## 2. 已有基础

项目已经具备以下可复用基础，新框架应在此之上演进，不重写已验证的控制链路：

- `src/control/tracking_contracts.py` 已定义参考、观测、命令和控制器合同；
- `src/simulation/tracking_pipeline.py` 已组合轨迹、控制器、后端和记录器；
- `src/simulation/scenes/trunk_trajectory_tracking.py` 已将通用合同适配到 SOFA 事件驱动场景；
- `src/evaluation/` 已提供记录和离线评估能力；
- 直线、椭圆、圆形、圆角三角形和圆角正方形已经通过批处理与人工可视化验收；
- `src/evaluation/trajectory_cli.py` 已验证“受控注册表 + 参数化单 case 入口”的可行性。

## 3. 核心目标

建立少量、按领域职责划分的稳定实验入口，并共享同一套执行内核，使场景、算法、
Pipeline、评估和可视化能够在受约束的框架中组合运行。

目标不是构建任意组合的通用平台，也不是将所有参数暴露到命令行，而是降低实验操作成本，
统一运行、日志、状态、验证、回传和产物合同，并停止按具体实验组合复制 Shell 脚本。

## 4. 设计原则

### 4.1 少量入口，不强求唯一入口

可以按实验领域保留少量入口，例如闭环跟踪、数据生成、模型训练和批量实验。入口数量不是
唯一指标，关键是边界稳定、职责清晰、不重复执行逻辑。

仅在下列情况允许新增入口：

- 实验生命周期存在实质差异；
- 需要明显不同的运行环境；
- 输入输出合同存在实质差异；
- 用户操作流程确实不同。

仅更换轨迹、控制器、seed、显示模式、输出名称或评估指标时，不应新增脚本。

### 4.2 有限的高层参数化

命令行主要表达“运行什么”，只暴露高层实验意图：

- Pipeline 类型；
- 算法或控制器选择；
- 输入轨迹、数据集、模型或预设选择；
- 输出 run ID；
- batch/GUI 和本地/远程等执行方式。

不提供任意字段的通用 `--set key=value`，不允许用户参数直接构造远程路径、Python 模块名或
未注册的组件组合。

### 4.3 琐碎参数配置化

以下内容默认由受版本管理的配置文件或预设管理：

- 仿真步长、控制频率和持续时间；
- 轨迹控制点、工作空间和随机生成边界；
- SOFA 求解器、插件和物理参数；
- 预热步数、deadline、评估阈值和输出字段；
- 颜色、线宽、标记大小等显示参数；
- 远程运行时路径和环境细节。

运行前应生成完整的有效配置快照，但不要求操作者在每次执行时理解或填写全部细节。

### 4.4 不变量由代码固定

以下约束应作为代码和 schema 的不变量，不开放给通用参数覆盖：

- `duration_s / dt` 必须为整数；
- 控制频率必须与仿真步长匹配；
- 轨迹起点必须与场景初始目标匹配；
- 控制器输出命令类型必须与后端兼容；
- run ID 不得覆盖已有运行目录；
- batch 和 GUI 必须使用相同的控制、记录和评估语义；
- 输出只能写入本次运行的指定目录。

## 5. 目标分层

```text
领域执行入口
        │
        ▼
受控 Pipeline / 算法 / 输入注册表
        │
        ▼
统一执行内核
  validate → preflight → prepare → run → verify → finalize
        │
        ▼
本地 / 远程 / batch / GUI 执行适配器
        │
        ▼
标准产物 → 评估 → 可视化 → 回传 / 汇总
```

场景、后端、记录器和评估器可由 Pipeline 定义固定。只有在项目中存在已验证的替代方案时，
才将其提升为用户可选参数。

## 6. 功能需求

### 6.1 领域执行入口

第一阶段优先统一闭环跟踪实验，提供受限的高层输入：

```bash
python scripts/experiment/run_tracking.py \
  --algorithm reference_goal \
  --input circle \
  --output 20261003_circle_reference_v1 \
  --mode batch
```

后续可根据实际生命周期增加数据生成、建模和批量实验入口，但它们必须复用统一执行内核。

### 6.2 受控注册表

注册单个组件的同时，优先声明已支持的 Pipeline 组合。未注册的算法、输入或组合必须拒绝运行。

### 6.3 有效配置

输入预设、算法配置、Pipeline 默认值和执行方式经验证后生成唯一有效配置。步数必须由
`duration_s / dt` 推导，不得再在 JSON、Python 注册表和 Shell 变量中重复维护。

### 6.4 统一运行生命周期

统一处理配置验证、环境预检、目录准备、运行、日志、超时、退出码、产物验证、完成状态和失败状态。
batch 与 GUI 的显示方式可以不同，但必须共享相同的配置解析、运行目录和 verifier。

### 6.5 批量实验

批量实验使用显式实验矩阵，只允许扫描 Pipeline 声明为可扫描的高层参数。每个 case 使用独立
run ID 和运行目录；单个 case 失败不覆盖或中断已完成结果；批量结束后生成汇总表。

### 6.6 统一结果验证与回传

不再按实验类型复制 `fetch_*.sh`。第一阶段通过 `scripts/remote/fetch_run.sh <profile> <run_id>`
统一回传；结果验证根据运行 manifest 和 Pipeline 产物合同执行，至少检查：

- `exit_code=0`；
- 存在 `COMPLETE` 且不存在 `FAILED`；
- 必需产物存在且非空；
- 轨迹行数、数值有限性和指标结构满足约定；
- 日志中不包含已声明的致命错误。

## 7. 标准产物

统一运行目录的基础结构：

```text
<run_id>/
├── requested_config.json
├── effective_config.json
├── metadata.json
├── stdout.log
├── exit_code
├── records/
├── metrics/
├── visualization/
└── COMPLETE 或 FAILED
```

第一阶段允许保留现有 `config.json`、`trajectory.csv` 和 `performance.json` 文件名，但新执行内核
必须对其语义统一建模，并在迁移方案中明确最终目录结构。

### 7.1 已实施进度（2026-10-05）

tracking 阶段 A 已完成受控入口与统一回传；阶段 B 已完成 `RunManifest`、有效配置快照、统一 SOFA
batch/GUI 命令构建、Python 运行生命周期和产物 verifier。本地 SSH 与远端工作区均通过
`run_experiment.sh` 薄边界接入同一内核。

已验收运行包括本地→SSH 直线 batch（200 步）、远端椭圆 batch（350 步）和远端椭圆 GUI（350 步）。
GUI 视觉现象由用户人工确认通过，三个运行均满足标准完成标记和产物合同。

脚本数从阶段 A 的 32 降至 31：本阶段用两个通用边界替代三份 tracking 专用运行器。原先约 25 的预测还
包含官方 demo、周期控制和其他实质不同生命周期的迁移；这些不会为满足数量指标而在本阶段强行合并，留待
后续独立设计和验收。

阶段 C 已将自动同步和 GPU smoke 的多份单用途脚本收敛为 `auto_sync.sh` 与 `smoke.sh` 的受控
子命令，并把 `baseline_trajectories` 登记为首个 tracking 批量矩阵。批量只扫描已批准的高层输入，
不开放场景路径、物理参数或任意 `--set` 覆盖；每个 case 独立运行，批次目录持久化 manifest 和汇总。
脚本数由阶段 B 的 31 降为 24；自动验证和两 case batch canary 已通过，GUI 场景效果已由用户确认，
阶段 C 正式验收完成。

## 8. 脚本规模基线与目标

截至 2026-10-03，`scripts/` 目录的脚本源码基线为：

| 类型 | 数量 |
|---|---:|
| Shell 脚本 | 41 |
| Python 脚本 | 1 |
| 有效源码脚本合计 | 42 |
| `run*.sh` | 17 |
| `fetch*.sh` | 5 |
| Python 运行入口 | 1 |

统计口径为 `scripts/` 下的 `.sh + .py`，排除 `__pycache__` 和 `.pyc`。

优化目标：

| 指标 | 当前 | 第一阶段 | 稳定目标 |
|---|---:|---:|---:|
| 脚本源码总数 | 42 | 不超过 24 | 20 左右，硬上限 22 |
| 面向用户的执行和回传入口 | 23 | 不超过 10 | 不超过 8 |
| 单个实验专用包装脚本 | 持续增长 | 停止新增 | 不超过 3 |

脚本数量是治理指标，不是为了达到数量而强行合并不同生命周期。安装、SSH 授权、连接检查和
工作区同步等基础设施脚本可以继续保留。

## 9. 验收标准

1. 新增轨迹只需增加组件、预设配置和测试，不新增 Bash。
2. 新增控制器只需注册算法及受支持组合，不复制 SOFA 场景和运行脚本。
3. batch 与 GUI 使用同一有效配置、Pipeline 和 verifier。
4. 步数只由有效配置推导，不再多处维护。
5. 单命令可以完成受支持实验的启动、状态记录和结果验证。
6. 批量实验中单 case 失败不破坏其他 case，并生成聚合结果。
7. 主要生命周期可使用 fake backend 或 dry-run 在本地测试。
8. 机器人运动、控制效果和场景显示仍按项目规则提供人工可视化验收方法。
9. 脚本源码总数在第一阶段不超过 24，稳定后不超过 22。

## 10. 非目标

- 第一阶段不建设任意组件自由拖拽或组合平台；
- 不为了形式上的“唯一入口”合并实质不同的生命周期；
- 不在框架改造中同时开发 PID、MPC 或学习控制器；
- 不修改已固定的上游 SoftRobots 示例资产；
- 不将密码、私钥、Token 或本地连接配置纳入实验配置或运行产物。
